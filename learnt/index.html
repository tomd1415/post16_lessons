1. The big picture

A small, self-hosted web platform that turned one working, pupil-tested Lesson 1 web pack for ICDL "Thinking like a Coder" into a 15-lesson course with local accounts, pupil work saved to a server with a full revision history, a sandboxed Python runner and teacher marking views. It runs as three Docker containers (Caddy for TLS, one FastAPI app that serves both the pages and the API, and PostgreSQL) and was built in phased commits over a week, 8–16 January 2026.

The starting point was a brief, plans/prompt_1 (kept locally; plans/ is git-ignored), written as instructions to an AI assistant. Its fixed requirements: keep Lesson 1's look and behaviour exactly; deliver in nine phases, each ending with a running demo, acceptance tests and a rollback plan; local accounts only (no Microsoft sign-in); store minimal personal data and delete it after two years; keep every save but do not show attempt history to pupils; and run Python on the server, safely. The history follows those phases closely: "Phase 0 complete and tested" (75d5298) through "Phase 8 finished" (1d47296) fell within three calendar days, 8–10 January. A .claude/settings.json appears in 3f83eb2 on 11 January, so Claude Code was in use by then; the history does not record which code an assistant wrote.

2. How a request travels

compose.yml defines three services. proxy is Caddy: it holds the TLS certificate, adds security headers, and forwards plain HTTP to api:8000. api is the FastAPI app. The unusual part is that it also serves the static pages: web/ is mounted read-only at /srv and the app ends with app.mount("/", StaticFiles(directory=STATIC_ROOT, html=True)). So one HTTP middleware sees every request, page or API, and that is what lets it send a logged-out visitor to the login page before any lesson HTML is returned (section 3). db is PostgreSQL 16 with its data in a named volume, pg_data.

The Docker socket mount is what makes the Python runner possible (section 5). It is also the most powerful thing in the stack: whatever can talk to that socket can start any container on the host, which in practice means root on the host. That is a general Docker fact; the repo's own guidance on it is "do not expose the Docker socket externally" (PROXMOXINSTALL.md).

TLS, in three stages

  1. Phase 2: https://localhost:8443 with tls internal. Caddy runs its own private certificate authority and signs a certificate for localhost. Browsers do not trust that authority, hence the README's "accept the browser warning".
  2. 9dcf298, "deployment tweaks": the site address became the host-less https://:8443 with tls internal { on_demand }, so Caddy issues a certificate for whatever name or IP address a request arrives on. The redirect on 8080 changed from a fixed localhost to {host} for the same reason.
  3. fcb33dc, "update network settings", the last commit: both HTTPS sites now load /etc/caddy/certs/server.crt and server.key, mounted from docker/certs/, and ports 80 and 443 are published next to 8080 and 8443. That folder is not in the repo, so the stack cannot start without a certificate being put there first. Why the change was made is not recorded; my inference is that it was to get a certificate the school PCs trust, which is what the mkcert section of docs/production-deployment.md describes for an IP-only LAN.
Verified: what a .env file can change Compose reads a .env file only to fill ${…} placeholders in the Compose file; it does not pass the file's contents into containers. compose.yml uses placeholders for POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB and SESSION_TTL_MINUTES, but writes every RUNNER_* value and RETENTION_YEARS=2 literally. While writing this page I ran docker compose --env-file probe.env config with a probe file setting RUNNER_TIMEOUT_SEC=99, RETENTION_YEARS=7, SESSION_TTL_MINUTES=123 and POSTGRES_DB=probe. Only the last two came through; the runner timeout stayed at 3 and retention at 2.

3. Accounts, sessions and who sees what

Accounts

Accounts are local, with three roles: pupil, teacher and admin. Instead of classes there is a cohort_year label, as the brief asked. Pupil usernames must follow the school's existing lastname.firstinitial format, enforced by the pattern ^[a-z][a-z\-']*\.[a-z]$ (valid_pupil_username in backend/app/main.py). Admins create users one at a time or by CSV import.

The very first admin is created with an unauthenticated POST /api/admin/bootstrap. It works exactly once: as soon as any admin exists it refuses with 403. That is a common first-run pattern, and its weak point is the window before it is used, when anyone who can reach the server could claim the admin account.

Passwords are hashed with Argon2id (backend/app/security.py: 2 passes, 64 MiB of memory, 1 lane). Argon2id is deliberately slow and memory-hungry, so a stolen hash is expensive to guess at.

Sessions and CSRF

Logging in creates a random session id (secrets.token_urlsafe(32)) and stores it in the sessions table along with a second random value, the CSRF token. The id goes to the browser as the tlac_session cookie: HttpOnly (page scripts cannot read it), Secure (HTTPS only), SameSite=Lax, lasting 480 minutes by default. Because the session lives in the database, logging out deletes the row and the cookie becomes worthless at once, which was one of Phase 2's acceptance tests.

The CSRF token is the defence against another website making a pupil's browser send a request with the cookie attached. SameSite=Lax already keeps the cookie off most requests started by other sites; the token is a second layer. Pages fetch /api/auth/me, which returns the token, and send it back in an X-CSRF-Token header on every state-changing call; csrf_guard compares it with the session's copy. Even where a foreign site can get the cookie sent, it cannot read the token from /api/auth/me, so it cannot forge the header.

Who can open which page

An HTTP middleware (auth_middleware) runs on every request. Requests under /api/ pass straight through and each endpoint checks for itself (require_teacher, require_admin). For pages: /login.html, /favicon.ico, /core/… and the lesson manifest are public; anything else needs a session, otherwise the visitor is redirected to /login.html?next=…. /admin… needs the admin role. Teacher-only paths are anything starting /teacher, anything containing /teacher/, and each lesson's index.html: in the Lesson 1 pack, a lesson's index.html was the teacher hub and student.html the pupil hub, and the platform kept that. Tests test_teacher_pages_blocked_for_pupils and test_admin_pages_blocked_for_teachers cover the rules.

Login backoff

Failed logins are slowed down twice over: per account (users.failed_login_count and locked_until) and per client address plus username (the login_attempts table). Both use compute_lock_seconds: nothing for the first two failures, then 30 seconds after 3–4, 120 after 5–6, 300 after 7–8 and 600 from 9. The brief asked for a "lockout/backoff strategy suitable for SEND context"; short, growing waits rather than a permanent lock fit that. The second table used to be a Python dictionary in memory, which every restart emptied; 3cae641 moved it into the database.

Verified The committed performance run (performance/results/test_results_20260112_003737.txt) shows the backoff working: attempts 1–3 with a wrong password returned 401, and attempts 4–10 returned 429 "Too many attempts. Try again shortly."

4. Saving pupil work

Lesson 1 already saved each activity in the browser's localStorage, under keys such as tlac_l1_a01_state, through a small store wrapper. The design inventory's rules included "do not change teacher mode behavior or storage keys", so Phase 3 put the server underneath that contract rather than replacing it (web/core/app.js):

Pupils only ever get the current state back; the revisions are for teachers (teacher-history.html). That is the brief's "store attempt history, but do NOT make it obvious to pupils". Since 0d0d1a9 each save also creates or updates an activity_marks row: the first save sets it to in_progress, later saves count attempts and timestamps, and a teacher's verdict is never overwritten (test test_hybrid_automark_on_save).

Verified The state column is declared as JSON().with_variant(JSONB, "postgresql") (backend/app/models.py): JSONB in production, plain JSON in the tests, which run against an in-memory SQLite database (backend/tests/conftest.py). One model works on both.

5. The Python runner

The brief wanted server-side Python with file input and output, turtle drawings and no risk to the server. The answer (backend/app/python_runner.py, Phase 6, dc34d26) is a fresh container for every press of Run, created through the host's Docker socket:

An asyncio.Semaphore lets only RUNNER_CONCURRENCY (2) runs happen at once; the rest wait their turn, which is the brief's "runs are queued; concurrency capped". The runner image defaults, in compose.yml, to post16_lessons-api, the app's own image, with automatic pulling off, so the school server never needs to download anything to run pupil code. The README calls this the offline fallback; the code's own default is python:3.12-slim.

Verified The tests never start Docker: conftest.py sets RUNNER_ENABLED=0, and test_python_run_happy_path swaps run_python for a fake. What they do check is how the commands are built (test_runner_exec_command_uses_inline_code, test_runner_file_listing_command_targets_tmp) and that unsafe file paths are refused (test_sanitize_files_rejects_parent_path).

6. Teacher views and marking

Phase 4 (e6527d5) built the first teacher view: filter pupils by cohort, a completion overview per lesson, a drill-down per pupil with their latest work, revision history and private notes, a Complete/Incomplete mark per activity alongside the objectives it maps to, and CSV export per lesson and per pupil (tests test_marking_and_overview, test_csv_exports, test_cohort_filters).

Phase 7 (6f43abc) added statistics. Completion per objective is counted as "activities mapped to the objective × pupils in scope". A "needs attention" list looks only at activities a pupil has started, and flags not_completed, many_revisions (5 or more saves) and stuck (no save for 7 days and not complete). Time on task is estimated from the first and last save, and only activities with two or more saves count. The brief said "do not overclaim precision", and the README repeats that the timings are approximate.

14 January (0d0d1a9, 9990ecf) added marking of individual answers (answer_marks, a JSON map such as {"q1": {"correct": true}}, with score = answers marked correct out of answers marked) and written feedback that the pupil can read. Every marking action writes an audit-log entry.

Verified set_answer_mark edits the answer_marks dictionary in place and then calls flag_modified(mark, "answer_marks"). SQLAlchemy notices when a column is given a new value, but not when the inside of a JSON value is changed. Without that call, the edit would never be written to the database.

7. Lessons as data

Everything about the course lives in web/lessons/manifest.json: the course details, a registry of 36 links from the teacher handbook, and 15 lessons, each with objectives, timings, resources, teacher resources and a list of activities. Each activity names the objectives it serves (objectiveIds) and the evidence expected. The catalogue page draws itself from the manifest, and the teacher statistics use the objective mapping. There are 39 activities in all: 8 in Lesson 1 (the original pack), 4 in Lesson 2, 3 in Lesson 3 and 2 in each of the rest.

  • Making packs. scripts/new_lesson_pack.py scaffolds a lesson in the Lesson 1 style: three auto-marked quick checks, guided notes, a main task in small steps, a reflection box and a teacher-only answer block. scripts/build_handbook_lessons.py parsed the handbook PDF to generate draft packs for lessons 3–15 (9985d90). The manifest marked 14 lessons as drafts at that point; since c05d36c, "all content added", all 15 are ready.
  • Link rot. scripts/link_registry_check.py checks every handbook link and writes a report; teachers can give any link a replacement URL or a local copy, or switch it off, from teacher-links.html. The overrides sit in data/link-overrides.json, outside the manifest, so regenerating content does not lose them.
  • Explicit instructions. f3b2b48 added numbered "how to" steps for every activity, as 485 lines inside app.js. The very next commit, 21c43ee, moved them into web/core/howto-map.json: content as data, not code.
  • Shuffled choices. 7dce1c9, "improving randomising", shuffles radio-button answers and drop-down options in the browser, keeping a leading "Select…" option in place.
  • Coding hints. a9d205f and 20a4fff added starter-code hints for each step of the coding activities.

One consequence of keeping Lesson 1's "teacher mode" as it was: the teacher-only answer guidance is part of the same HTML file the pupil loads, hidden with display:none and shown when a staff member switches teacher mode on (for example in lesson-3/activities/02-inputs-and-outputs.html). A pupil who opens "view source" can read it. Only the separate teacher/ pages (lesson plan, cards, answer key) are actually blocked for pupils.

8. Operations and monitoring

  • Backups (scripts/backup.sh): pg_dump through docker compose exec into db.sql.gz, a tar of data/ and reports/, and a backup.meta file, in backups/backup_YYYYMMDD_HHMMSS/; old backups are pruned (30 days, keep the last 14). scripts/restore.sh refuses to run without --force, because it drops the whole database schema before loading the dump.
  • Retention (backend/app/retention.py): a pupil is due for deletion when the latest of their last login, account creation, last save and last revision is more than two years old. The default is a dry run that lists what would go; --apply deletes; staff are left alone unless --include-staff is given (test test_retention_purge_deletes_old_pupil).
  • Audit and DPIA. Teacher and admin actions go to an audit log with an admin page; docs/dpia-summary.md lists what personal data is held, why, for how long and who sees it.
  • Monitoring. backend/app/metrics.py defines Prometheus counters and histograms (requests, logins, saves, Python runs). compose.monitoring.yml adds Prometheus (30-day retention) and Grafana with a ready-made dashboard; admin-metrics.html shows a summary inside the app itself.
  • Schema changes. The app creates its tables at start-up with Base.metadata.create_all, which creates missing tables but never changes existing ones. New columns therefore needed a hand-written migration (see the traps).

11. Traps

Trap: a feature commit that deletes features 4fb501b was described as "add admin for users", and it did add that. It also took out API rate limiting, real client addresses and the metrics endpoints, because main.py was rewritten from a version that predated them (section 9). Four follow-up commits restored part of it; two features stayed gone, and the documentation was changed to fit. A commit message only says what was meant to change.
Trap: .gitignore does not untrack a file scripts/run_playwright_tests.sh, which exports usernames and passwords for the Playwright test accounts, was committed in 3cb3fbb and 73cc1ca. Two hours later 7dce1c9 added run_playwright_tests.sh to .gitignore. That only stops untracked files being added; the committed file stayed tracked, was pushed to GitHub, and is still in the repo. The same test passwords are written into performance/*.py. Ignoring a file afterwards needs git rm --cached, and a password that has been pushed needs changing, because the history keeps it.
Trap: a green tick over zero successes The committed performance results print "✓ All requests succeeded (no rate limiting triggered at this load)" directly below "Successful requests: 0", and "✓ All executions succeeded" below "Successful executions: 0". The save requests were going to POST /api/activity/state, a path with no lesson or activity in it, which only accepts GET (hence 405). The run requests got 403 because the scripts read the CSRF token from the login reply, which does not contain it; the token comes from /api/auth/me. The save and run benchmarks therefore measured nothing, and the summary still looked like a pass.
Trap: a .env file does not reach the containers PROXMOXINSTALL.md said to put overrides such as RUNNER_TIMEOUT_SEC and RETENTION_YEARS in .env. Because compose.yml writes those values literally, a .env file changes nothing (checked with docker compose config, section 2). They have to be edited in the api service's environment: list. The guide was corrected on 2026-10-06.
Trap: create_all never alters a table When 0d0d1a9 added six columns to activity_marks, a fresh database got them, because create_all builds missing tables from the models. An existing database did not, because create_all skips tables that already exist. ab3047a "added DB migration" and fa3041d (backend/migrations/README.md) added hand-written ALTER TABLE … ADD COLUMN IF NOT EXISTS SQL to paste into psql.
Trap: Docker's archive calls and a tmpfs /tmp The runner's /tmp is a tmpfs, an in-memory filesystem. The README note added in ea6d1af says the code is passed inline because file-based execution gave intermittent "can't open file '/tmp/main.py'" errors "caused by relying on Docker archive uploads into tmpfs", and warns not to switch back. Collecting output files had the matching problem: 027a05f "save files is now working" replaced get_archive("/tmp") with an exec'd script that prints the files as JSON. The repo records the symptom and the workaround, not the cause. My understanding is that Docker's archive API reads and writes the container's own filesystem, not filesystems mounted over it, but I have not verified that here.
Trap: a strict CSP and inline scripts 3cae641 added a Content Security Policy with script-src 'self', which blocks scripts written inside the HTML. The lesson pages use inline scripts, so 96fe184 added 'unsafe-inline' with the comment "needed for inline scripts and styles" and a TODO to move to nonces or hashes. A CSP has to match how the pages are built, or it breaks them.
Trap: SQLite in the tests, PostgreSQL in production SQLite hands back datetimes without a time zone, while the code compares them with datetime.now(timezone.utc); Python refuses to compare the two kinds. Hence ensure_timezone_aware ("for SQLite compatibility") in rate_limit.py, and the same fix-up in the session-expiry check. Fast in-memory tests are worth having, but the test database is not the real one.
Trap: two Compose files, one network compose.monitoring.yml first joined an external network called tlac-network, which compose.yml never created. a147e6e "monitoring fixes" gave both files' default network the explicit name tlac-network, so Prometheus can reach api:8000 whichever file starts first.
Trap: docs that describe last week's code On 2026-10-06 the docs still said TLS used Caddy's internal CA (README.md, docs/dpia-summary.md, docs/monitoring-guide.md), although fcb33dc, the last commit, had replaced it with a supplied certificate; no doc was touched in that commit. docs/api-reference.md still listed per-endpoint rate limits, contradicting its own "Rate Limits" section and the code. These were corrected in the documentation commit made alongside this page.

12. General lessons

Review the deletions After any large rewrite of a file, by a person or an assistant, read the removed lines as carefully as the added ones. git diff --stat showed 418 deletions in 4fb501b; a search of the old file for function names (get_client_ip, ApiRateLimiter) would have found the losses in a minute.
Test the wiring, not just the part A unit test of a rate limiter proves the limiter works, not that anything uses it. For every safety feature, keep at least one test that goes through the real endpoint, such as "the 61st save in a minute gets 429".
A harness that cannot fail is not a test Print a pass only after checking that something succeeded. "0 successful, 0 rate limited" should be reported as a failure of the test itself, not as "no rate limiting triggered".
Keep the old contract, change what is underneath Server saving was added without touching Lesson 1's storage keys: the existing store.set call simply started queueing a sync as well. Every existing activity got server saving and offline resilience without being edited.
Decide before you reconcile When code and docs disagree, first decide which one is right, then fix the other. On 14 January the docs were edited to match code that had lost two features by accident, which turned a regression into the documented design.
Secrets never go in, not "go in, then get ignored" Test credentials belong in an environment file that is ignored before it is ever committed: export_vars_for_test.sh was listed in .gitignore a minute after it was created (9b6477b) and has never been in the repo. Once a secret is committed and pushed, the only real fix is to change it.

14. Test yourself

Why does the FastAPI app serve the static lesson pages itself instead of leaving them to Caddy? So that one middleware sees every request. It can redirect a logged-out visitor to the login page, and keep pupils off teacher and admin pages, before any HTML is sent. If Caddy served the files directly, the app would never see those requests.
The session cookie is HttpOnly, so page scripts cannot read it. How does a page get the CSRF token, and why can't a hostile website do the same? The page fetches /api/auth/me, which returns the token stored with the session, and sends it back in the X-CSRF-Token header. Even if a hostile site manages to get the cookie sent with a request (SameSite=Lax already blocks most cases), the browser will not let that site read the reply from /api/auth/me, so it never learns the token.
Why does logging out really end a session here, rather than just deleting the cookie? The session is a row in the database, identified by the cookie's random id. Logout deletes that row, so even a copy of the cookie stops working at once.
A pupil saves while the classroom Wi-Fi is down, then closes the tab. What happens to the work? It is in localStorage twice: the activity state itself, and an entry in the pending list (tlac_sync_pending). The next time a page loads in that browser, or the browser comes back online, flushPending posts it to the server, and removes the entry only after a successful reply.
How does the platform keep every attempt without showing attempt history to pupils? Each save updates one current-state row (all the pupil's page ever loads) and also appends a revision row. Only teacher pages and teacher-only API endpoints read the revisions.
Name four limits on a runner container, and say what each protects against. Any four of these. No network: the code cannot reach anything. 3-second timeout with SIGKILL: infinite loops. 128 MB of memory and half a CPU: one pupil starving the server. 64 processes: fork bombs. All capabilities dropped, no-new-privileges and user nobody: escalation inside the container. 32 MB tmpfs: filling the disk. And at most 2 runs at once (the semaphore): the server overall.
How do turtle programs work in a container with no screen? The bootstrap installs its own turtle module, which records each line as the program moves and writes turtle.svg when the program ends. It also installs a tkinter that does nothing. The SVG is collected like any other output file and shown in the page.
I set RUNNER_TIMEOUT_SEC=10 in .env and restarted. Why is the limit still 3 seconds? Compose uses .env only to fill ${…} placeholders, and compose.yml writes RUNNER_TIMEOUT_SEC=3 literally with no placeholder. Edit the value under the api service's environment: instead.
A new column was added to a model, the API restarted cleanly, and the first query using it fails on the school server but not on a fresh install. Why? Base.metadata.create_all creates missing tables but never adds columns to existing ones. A fresh database got the new column; the existing one needed ALTER TABLE … ADD COLUMN (as in backend/migrations/).
Every rate-limiter test still passed after the save and run endpoints stopped being rate-limited. Why? The tests called the ApiRateLimiter class directly. None of them sent 61 saves to the real endpoint, so nothing noticed that the endpoints no longer called the class.
Why did "add run_playwright_tests.sh to .gitignore" not keep its passwords out of GitHub? .gitignore only affects files Git is not already tracking. The script had been committed two hours earlier, so it stayed tracked and was pushed. It needs git rm --cached, and the passwords need changing.
Why can a pupil read the teacher's answer guidance on an activity page, but not the answer key page? The guidance block is part of the activity's own HTML, hidden with display:none until teacher mode shows it, so "view source" reveals it. The answer key lives under /lessons/lesson-N/teacher/, which the middleware refuses to send to a pupil.
Why does set_answer_mark call flag_modified? It changes the inside of the answer_marks JSON dictionary. SQLAlchemy only notices when a column is given a new value, so without flag_modified the change would not be saved.

15. Still to check

These come from reading the code while writing this page on 2026-10-06. None was run.

  • Can Prometheus actually scrape /metrics? The login middleware redirects any request without a session that is not under /api/ and not on the public list, and /metrics is not on the list (is_public_path). No test covers it. Start the monitoring stack and look at Prometheus's Targets page.
  • The start-up retry. lifespan records an error when create_all fails but never clears it after a later attempt succeeds, so a database that is slow on first boot would still stop the API (the restart policy then tries again).
  • Shared browsers. The localStorage keys are not per user, and logout clears only tlac_role. On a PC where pupils share one browser profile, the next pupil could see the previous pupil's local answers, and an unsent pending save could be sent under the next login.
  • Pupil input files still reach the runner only through put_archive into the tmpfs /tmp, the mechanism the README calls unreliable. Run a file-reading activity repeatedly.
  • Decide about the two lost features: wire ApiRateLimiter back into the save and run endpoints and restore the forwarded-address handling (or start uvicorn with proxy headers), or leave them documented as off.
  • Teacher-only answers in pupil-loaded HTML: decide whether that matters for this course.
  • Committed test passwords: change them, and untrack scripts/run_playwright_tests.sh.
  • The performance scripts: fix the save path and take the CSRF token from /api/auth/me, then measure saves and runs for real.

16. Glossary

Reverse proxy
A server that receives the browser's requests and passes them on to the real application. Here Caddy holds the TLS certificate and adds security headers, and the app only ever sees plain HTTP from Caddy.
TLS termination
Decrypting HTTPS at the proxy, so the traffic behind it (proxy to app, inside the Docker network) is plain HTTP.
Caddy internal CA
Caddy's built-in private certificate authority (tls internal). The encryption is real, but browsers do not trust the authority until its root certificate is installed. on_demand makes Caddy issue a certificate for whatever host name or IP a request arrives on.
Compose interpolation
Docker Compose replacing ${VAR:-default} in the Compose file with values from the shell or a .env file. It does not inject the .env file into containers.
StaticFiles
FastAPI's (Starlette's) way of serving a folder of files from inside the app, so the app's middleware applies to them.
Session cookie flags
HttpOnly: page scripts cannot read the cookie. Secure: sent over HTTPS only. SameSite=Lax: not sent on most requests started by other websites.
CSRF
Cross-site request forgery: another site making your browser send a request that carries your cookie. Prevented here by a per-session token that must be sent back in a header.
Argon2id
A password-hashing method designed to be slow and memory-hungry, so guessing passwords from a stolen hash is expensive.
Backoff
Making a client wait longer after each further failure, instead of locking the account for good.
Offline-first sync
Saving to the device first and sending to the server when possible, so a dropped connection loses nothing.
Revision
One stored copy of an activity's state per save. Teachers can see the history; pupils only get the latest.
Docker socket
/var/run/docker.sock, the Docker daemon's control channel. Whatever can use it can start any container on the host.
tmpfs
A filesystem held in memory, mounted into a container; it vanishes when the container is removed.
exec (Docker)
Running an extra command inside a container that is already running. The runner uses one exec for the pupil's code and one to collect output files.
Semaphore
A counter that lets only a fixed number of tasks into a section at once. Here, at most two Python runs.
create_all
SQLAlchemy's "create any tables that are missing" call. It never alters an existing table.
flag_modified
SQLAlchemy's way of marking a column as changed when its contents were edited in place, such as a key changed inside a JSON dictionary.
Prometheus / Grafana
Prometheus collects numeric metrics by "scraping" an HTTP endpoint at intervals; Grafana draws dashboards from them.
DPIA
Data Protection Impact Assessment: the record of what personal data a system holds, why, for how long and who can see it.
Retention purge
Deleting personal data once it is older than the agreed period (two years after last activity here), with a dry run first.
Lesson manifest
The single JSON file that describes the course, its lessons, activities, objectives and links, from which the pages and statistics are built.
Link registry
The list of external handbook links, with a checker and teacher-set replacements for links that have died.
